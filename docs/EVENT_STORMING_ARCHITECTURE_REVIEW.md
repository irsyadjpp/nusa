## 1. Domain Events

### 1.1 Aggregate: TPSet (Teaching Plan Set)

#### Create Events
- **TPSetCreated** - When a new TP Set is created from CP
  - Trigger: CreateTPSetCommand
  - Data: TPSet ID, CP ID, Version No, Generation Source, Generated By
  - Policies: TPSet must reference valid CP, Version No must be >= 1

#### Update Events
- **TPSetStatusChanged** - When TP Set status changes
  - Trigger: UpdateTPSetStatusCommand
  - Data: TPSet ID, Old Status, New Status, Changed By, Timestamp
  - Policies: Only valid status transitions allowed (DRAFT→UNDER_REVIEW→APPROVED/REJECTED)

#### Approval Events
- **TPSetApproved** - When TP Set is approved
  - Trigger: ApproveTPSetCommand
  - Data: TPSet ID, Approved By, Approval Date, Comments
  - Policies: Only SystemAdmin or Principal can approve, Must be in UNDER_REVIEW status

- **TPSetRejected** - When TP Set is rejected
  - Trigger: RejectTPSetCommand  
  - Data: TPSet ID, Rejected By, Rejection Reason, Rejection Date
  - Policies: Only SystemAdmin or Principal can reject, Must be in UNDER_REVIEW status

#### Archive Events
- **TPSetArchived** - When TP Set is archived
  - Trigger: ArchiveTPSetCommand
  - Data: TPSet ID, Archived By, Archive Date
  - Policies: Only APPROVED TP Sets can be archived

## 3. Policies

### 3.1 Workflow Status Policies

**Valid Status Transitions:**
```
DRAFT → UNDER_REVIEW → APPROVED → ARCHIVED
                ↘ REJECTED → ARCHIVED
```

**Policy Rules:**
1. Only DRAFT artifacts can be edited
2. Only UNDER_REVIEW artifacts can be approved/rejected
3. Only APPROVED artifacts can be used in production
4. Only APPROVED artifacts can be archived
5. REJECTED artifacts can be returned to DRAFT for revision

### 3.2 Version Control Policies

**Version Management:**
1. Version numbers must be sequential (increment by 1)
2. Only current version can be active
3. Previous versions must be archived before creating new version
4. Version history must be preserved for audit trail
5. Version rollback requires approval

**Snapshot Policies:**
1. All version-dependent data must be snapshot at creation
2. TP snapshots include: KKTP Criteria, Learning Objectives, Time Allocation
3. Assessment snapshots include: TP ID, TP Version No, Success Criteria
4. Snapshots are immutable - new version = new snapshot

### 3.3 Approval Policies

**Approval Authority:**
1. TP Sets: SystemAdmin, Principal
2. TP: SystemAdmin, Principal
3. Assessments: SystemAdmin, Principal
4. ATP Sets: SystemAdmin, Principal
5. Narrative Reports: SystemAdmin, Principal

**Approval Requirements:**
1. Artifact must be in UNDER_REVIEW status
2. Artifact must pass all validation rules
3. Approver must have appropriate role permissions
4. Approval must include approver ID and timestamp
5. Rejection must include reason for rejection

### 3.4 AI Generation Policies

**AI Agent Integration:**
1. AI generation confidence must meet minimum threshold (configurable)
2. AI agent version must be recorded for audit trail
3. AI-generated artifacts must be in DRAFT status for review
4. AI generation must preserve all related entity snapshots
5. AI generation source must be tracked (AI Generation ID)

**AI Agent Usage:**
1. TP Agent: Generate TP from CP (minimum 80% confidence)
2. ATP Agent: Generate ATP from TP (minimum 80% confidence)
3. Modul Ajar Agent: Generate Modul Ajar from ATP (minimum 80% confidence)
4. Assessment Agent: Generate Assessment from Modul Ajar (minimum 75% confidence)
5. Rubric Agent: Generate Rubric from Assessment (minimum 75% confidence)
6. Narrative Report Agent: Generate Report from Evidence (minimum 70% confidence)

### 3.5 Curriculum Hierarchy Policies

**CP → TP → ATP → Modul Ajar Chain:**
1. TP must reference valid CP
2. TP must include KKTP Criteria from CP
3. ATP must reference valid TP Set
4. ATP must follow weekly sequence pattern
5. Modul Ajar must reference valid ATP
6. Assessment must reference approved TP
7. Evidence must reference approved Assessment
8. Narrative Report uses evaluated Evidence

**Version Consistency:**
1. Assessment must snapshot TP version at creation
2. Cannot link Assessment to archived TP version
3. Version validation on all cross-references

### 3.6 Evidence Collection Policies

**Evidence Lifecycle:**
1. Evidence can be collected for approved assessments
2. Evidence must be linked to specific student
3. Evidence status follows: COLLECTED → LINKED → EVALUATED
4. Only EVALUATED evidence can contribute to achievement
5. Evidence can have multiple evaluations (revision history)

**Rubric Requirements:**
1. Rubric must be assigned before evaluation
2. Evaluation must use currently assigned rubric
3. Rubric change requires evaluation revision
4. Rubric deletion prevents new evaluations but keeps historical data

### 3.7 Achievement Calculation Policies

**Calculation Rules:**
1. Achievement is calculated on-demand (not persistent)
2. Achievement follows KKTP criteria from TP
3. Performance levels based on KKTP mastery thresholds
4. Competency progress based on TP completion and assessment results
5. Class achievement aggregates student achievements

**Data Requirements:**
1. Assessment results must be available
2. TP KKTP criteria must be accessible
3. Evaluation data must be complete
4. Student-TP mapping must be current

### 3.8 Security Policies

**Permission Requirements:**
1. User must be authenticated
2. User must have appropriate role for action
3. Granular permissions for education domain (tp:*, assessment:*, etc.)
4. School-based data isolation
5. Student data privacy protection

**Data Access:**
1. Teachers can only access their school/class data
2. Admins have broader access within their school
3. SystemAdmins have full system access
4. Read permissions for viewing, Write permissions for modification

## 5. Aggregates

### 5.1 TPSet (Aggregate Root)

**Aggregate Root:** Yes

**Lifecycle Events:**
- **Create:** TPSetCreated
- **Update:** TPSetStatusChanged
- **Approve:** TPSetApproved
- **Reject:** TPSetRejected
- **Archive:** TPSetArchived

**Invariants:**
- TPSet must reference valid CP
- Version No must be >= 1
- Status must follow workflow rules
- Only approved TP Sets can generate ATP sets

**Relationships:**
- CP → TPSet (Many-to-One)
- TPSet → TPs (One-to-Many)
- TPSet → User (Many-to-One)

---

### 5.2 TP (Aggregate Root)

**Aggregate Root:** Yes

**Lifecycle Events:**
- **Create:** TPCreated
- **Update:** TPUpdated, TPKKTPCriteriaUpdated
- **Version:** TPVersionCreated, TPVersionArchived
- **Approve:** TPApproved
- **Archive:** (Via TP Set archive)

**Invariants:**
- TP must reference valid TP Set
- Sequence Number must be unique within TP Set
- KKTP Criteria must be valid
- Only current version can be modified
- Version transitions must be sequential

**Relationships:**
- TPSet → TP (One-to-Many)
- CP → TP (Many-to-One via TPSet)
- TP → Assessment (One-to-Many)

**Embedded Value Objects:**
- KKTPCriteria (embedded as JSONB)

---

- **Create:** AssessmentCreated
